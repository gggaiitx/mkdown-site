### 1.3 选型结论（明确）

**✅ 推荐：md-editor-v3（Vue 3）为唯一编辑器内核；若团队坚持 React 技术栈，则用同作者的 md-editor-rt。**

**不建议采用 editor.md，也不要为它做适配层。**

### 1.4 决策理由

1. **维护风险是决定性因素**：editor.md 最后一次代码提交停在 **2019-05-09**（7 年多前），最新 release 是 **2015 年的 v1.5.0**，累积 **580 个未处理 Issue**。它本质上是一个停止维护的项目。任何新项目把核心编辑器押在它身上，等于把长期可维护性交给一段冻结的代码。
2. **License 不构成障碍**：两者均为 **MIT**，均可商用、可修改、可闭源分发。这是"两者都能选"的前提，因此**不能**用 License 当理由剔除任一方——差异全在工程与维护层面。
3. **技术栈代差**：editor.md 基于 jQuery/Vue2 时代体系，且需 jQuery + CodeMirror + FontAwesome + KaTeX + prettify + flowchart + sequence-diagram 等一大串外部依赖；在 Tauri 这种现代 WebView 环境里属于"上古栈进新壳"，打包体积、依赖冲突、安全审计都是负担。md-editor-v3 是原生 Vue 3 + TS + JSX，构建体系现代，周下载量是 editor.md 的 **约 35 倍**（34,411 vs 968），社区实际使用度碾压。
4. **Star 数不能代表现状**：editor.md 的 14,315 Star 是 2015–2019 年红利期积累的历史存量，**不代表当前活跃度**；md-editor-v3 的 2,596 Star 是持续增长的现代项目，且作者同时在维护 React 版与扩展包生态（@vavt/*），是"活着的项目"。
5. **开箱即用的功能更全**：Mermaid、KaTeX、图片粘贴上传、预览主题、prettier 美化、PDF 导出扩展、纯预览组件 `MdPreview`、目录组件 `MdCatalog`、按需引入——这些正是"编辑器 + 阅读器"双形态所需，md-editor-v3 原生覆盖，editor.md 大量需自研。
6. **不需要做可插拔适配层**：适配两层编辑器内核会显著抬高复杂度与测试成本，而收益是一个已停止维护的备选项——投入产出比不成立。**保留一条干净的主线即可。**

**一句话**：editor.md 是"曾经很好、现已沉睡"的老将；md-editor-v3 是"功能更全、正在活跃维护"的现役选手。选 md-editor-v3。

## 2. 产品定义

### 2.1 定位（一句话）

**MkDown 是一款纯本地、离线优先、中文原生的 Markdown 编写与阅读桌面工具，面向需要长期积累与复用技术文档、招标方案的重度写作者。**

### 2.2 核心价值（3–5 条）

1. **本地即全部**：文档、图片、配置全部落在本机磁盘，不上云、不登录、不联网即可完整使用——满足医疗/投标类文档的隐私与保密诉求。
2. **写得快**：分栏预览 + 快捷键 + 大纲导航 + 模板复用，让"招标方案分段写作"这类结构化长文写作效率显著提升。
3. **读得舒服**：一个按键在"编辑"与"阅读"间切换，阅读态提供目录、主题、字号、导出。
4. **文档库可管理**：以工作区/文件夹方式组织多文件，支持树形浏览、搜索、最近打开、模板库。
5. **轻、稳、原生**：Rust + Tauri 外壳，启动快、内存占用低、安装包小，优于 Electron 类工具。

### 2.3 目标用户与典型场景

**核心用户画像**：飞总——医疗信息化技术工程师，Windows + 中文环境，日常产出招标方案、技术文档、需求说明、周报等，客户对文档保密性有要求。

典型场景：

- **S1 招标方案分段写作**：一个方案拆成多个 .md（概述 / 技术方案 / 实施计划 / 售后），左侧文件树管理，右侧大纲快速跳转某章节继续写。
- **S2 模板复用**：把常用方案骨架存为"模板库"，新建文件时一键套用，避免每次从零起稿。
- **S3 离线隐私写作**：在客户现场/无网环境打开软件，所有内容不出本机。
- **S4 文档库沉淀与检索**：多年积累的 .md 集中在一个工作区，按关键字快速找回历史方案。
- **S5 阅读态评审**：把写好的方案切到阅读模式，配目录与主题，用于审阅、投屏讲解。
- **S6 图文混排**：粘贴截图自动保存到文档同级 `assets/` 目录并写入相对路径，保证文档可整体搬迁。
- **S7 交付导出**：将 Markdown 导出为 PDF / HTML 交付给非技术人员查看。

## 3. 用户故事（12 条）

1. 作为技术文档写作者，我希望**打开软件就能看到上次的工作区并继续写**，以便不用每次都重新找文件。
2. 作为招标方案作者，我希望**在左侧文件树里组织多份 .md**，以便把一个大方案拆成多个文件分块维护。
3. 作为重度写作者，我希望**编辑区与预览区实时分栏显示**，以便边写边看排版效果。
4. 作为阅读者，我希望**一键切换到纯阅读模式**，以便专注审阅而不被编辑工具栏干扰。
5. 作为长文作者，我希望**右侧有实时大纲（TOC）且能点击跳转**，以便在数千字方案里快速定位章节。
6. 作为方案撰写者，我希望**新建文件时能从模板库套用骨架**，以便复用历史方案结构。
7. 作为图文文档作者，我希望**直接粘贴截图就自动落盘到 assets 并插入相对路径**，以便图文并茂且文档可整体搬迁。
8. 作为技术作者，我希望**支持 Mermaid 流程图与 KaTeX 公式**，以便在方案里画架构图和写算法说明。
9. 作为交付方，我希望**把 .md 导出为 PDF / HTML**，以便发给不看 Markdown 的客户。
10. 作为中文用户，我希望**界面与快捷键提示默认中文**，以便零学习成本上手。
11. 作为隐私敏感用户，我希望**全程离线、数据不出本机**，以便满足医疗/投标保密要求。
12. 作为多设备用户，我希望**暗色/亮色主题与字号可切换并记忆**，以便在不同环境长时间阅读不疲劳。
13. 作为重度用户，我希望**用快捷键完成加粗/标题/插入表格等常用操作**，以便手不离键盘高效写作。
14. 作为需要整理资料的人，我希望**在工作区内按关键字搜索文件名与正文**，以便快速找回历史文档。

## 7. Tauri WebView 集成要点与坑点（给架构师）

1. **前端选型需与内核一致**：md-editor-v3 是 **Vue 3** 组件库。因此前端建议 **Vue 3 + Vite + TypeScript**（而非默认的 React + MUI）。若团队必须用 React，请改用同作者的 **md-editor-rt**（MIT、475★、2026-09-16 活跃），功能与 API 基本对齐，可避免"React 壳里塞 Vue 组件"的桥接成本。**不建议 Vue/React 混用**。
2. **文件系统走 Rust 侧**：打开/保存/读取工作区、图片落盘等 IO 应通过 Tauri 的 Rust 命令（`#[tauri::command]`）或官方 `fs` 插件实现，避免在前端 WebView 里直接操作路径，也更利于权限收敛。
3. **Windows = WebView2（Chromium 系）**：与 md-editor-v3 的兼容性最好，主要验收环境。注意 WebView2 Runtime 依赖：Win10/11 通常自带，老系统需引导安装。
4. **macOS = WKWebView**：需实测 CSS/字体差异；`kb` 级交互基本一致，但 `contenteditable`、剪贴板 API 行为与 Chromium 有差异，图片粘贴建议在 Rust 侧兜底。
5. **Linux = WebKitGTK**：最容易出兼容问题的平台，作为"可运行"而非"优秀"目标。
6. **本地资源路径**：预览态引用本地图片需经 Tauri 的 asset 协议（`convertFileSrc` / `asset://`），不能直接用 `file://`，否则 WebView 会拦截。
7. **CSP**：Tauri 默认 CSP 需放行编辑器所需的内联样式/字体；建议放宽到满足编辑器运行的最小集合，不要图省事全关。
8. **打包体积**：md-editor-v3 支持按需引入（>=4.0.0），Mermaid/KaTeX 体积较大，建议懒加载，避免安装包膨胀。

## 8. 待确认问题（需飞总拍板）

1. **文档库组织方式**：用"选定一个根文件夹作为工作区（类 VSCode）"，还是"维护多个独立的工作区可随时切换"？（影响 P0-5 / P2-4）
2. **是否必须所见即所得**：分栏预览是否满足需求？还是需要类 Typora 的即时渲染（WYSIWYG）？后者会显著增加工作量（当前内核不原生支持）。
3. **导出格式优先级**：PDF 与 HTML 之外，是否需要 **Word(.docx)** 导出？（影响 P1-3 / P2-3）
4. **图片存储策略**：图片统一存当前文档同级 `assets/` 目录，还是存全局 `attachments/` 目录？（影响文档搬迁与引用路径）
5. **是否需要公式/图表**：招标方案中 KaTeX 公式与 Mermaid 流程图是否为刚需？（影响 P1-1/P1-2 是否进 MVP）
6. **自动保存策略**：是否默认开启自动保存？间隔多少（如 30s）？是否需要本地版本历史（P2-6）？
7. ~~**前端技术栈确认**~~ ✅ **已确认（2026-09-23，飞总拍板）**：采用 **Vue 3 + Vite + TypeScript + Pinia**（配合 md-editor-v3），不使用 React / md-editor-rt。技术栈自此冻结。
8. **三平台范围**：MVP 是否只保证 Windows，macOS / Linux 延后？（影响测试与验收成本）
9. ~~**PDF 导出实现**~~ ✅ **已确认（2026-09-23，飞总拍板）**：走 **WebView 打印**路线（预览 HTML → WebView2 打印为 PDF），不引入 headless 渲染组件；中文字体/排版与浏览器渲染一致。
10. **应用命名与图标**：产品对外名称是否就用 MkDown？是否需要自定义图标与安装信息（发布者、版本号规则）？
